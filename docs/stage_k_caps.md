# 用 coarse/fine 状态限制 k

启用 `--stage-aware` 后，运动阶段决定允许的最大 k，原有计时调度器在允许范围内选择最小可行 k。没有候选满足时间预算时，使用阶段允许的最大候选并记录不可行；不为减少等待突破阶段上限。

本版固定执行长度 E=10，与模型每次生成的 H=10 个动作一致。命令行、调度器、阶段配置与 broker 均拒绝其他执行长度，客户端校验服务端声明的预测长度，broker 校验每次实际返回的 10×7 动作。除任务提前结束，整块 10 步全部执行，不截取前 5 步或 8 步。

阶段请求上限为：精细阶段 `floor(E/2)=5`，粗操作 `floor(2E/3)=6`。实际生效上限还受单块剩余动作数与权重上下文长度约束：

```text
hard_max_k = min(E-1, 9)
fine_max_k = min(floor(E/2), hard_max_k)
coarse_max_k = min(floor(2E/3), hard_max_k)
```

E=10 时，精细和粗操作的请求上限与实际上限均为 5/6，候选集合自动为 0..6。上限只限制允许的最大 k，调度器仍根据实际耗时选择范围内最小可行值。

可显式配置上限 0。`k=0` 表示先执行完本块，再获取新观测，以空动作上下文同步请求下一块。它会产生交接等待，不改变本块执行长度 E，也不意味着每个动作后都重新观察。

## 状态来源

运动阈值源于 `openpi_async_stage` 的 `async_stage_target20_20261113/thresholds.json`，原配置原样保存在 [configs/stage_target20.json](../configs/stage_target20.json)。运行时只读取 StageConfig 中的运动、夹爪和滞回字段，原 JSON 中的执行长度、计时窗口、分位数和 overlap 规则不替代本仓库的计时调度参数。

- 使用最新已执行的末端 xyz 位置和模拟时间，分别计算两个相邻 5 步窗口的速度向量。
- 速度是最新窗口速度向量的模；变化强度是两个窗口速度向量差的模除以最新窗口时长。
- 历史不足、低速度、高运动变化、即将切换夹爪或位于夹爪保护期时进入精细阶段。
- 退出精细阶段需要满足原阈值的滞回与连续稳定次数。
- 夹爪保护使用实际控制/模拟时间，不使用推理等待墙钟时间。每回合重置状态机和运动历史，计时估计保留跨回合样本。

与旧 stage 实验的差异：旧实现每块执行 5 步；本仓库固定 E=10。为覆盖整块内夹爪事件，当前检查本块将执行的全部 E 步动作，原实现检查前 5 步。其余运动窗口和阈值沿用原配置。新阶段占比不保证为 20%，也不能继承旧实验的成功率结论。

这些是运动启发式 coarse/fine 标签，不是视觉语义识别出的接近、抓取、搬运或放置真值，也不读取物体真值位置或 benchmark 成功信号。

## 决策与交接

每个新 chunk 安装时读取最新运动历史和本块预测动作，冻结 stage、k_max 与 k。本块的上限变小会立即截断 k，即使处于冷启动或原计时调度器的慢下降期；上限变大后仍根据实际请求和动作时间选择 k。

块内发生的状态变化在下个 chunk 决策时生效。已经提交给模型的上下文全部执行完，结果早到时缓冲。当前没有块内取消或重规划，不能声称每次进入接触状态都能立即降低已承诺的 k。

默认无 `--stage-aware` 时保持原计时模式，仍为候选 2..9。固定 k 对照与阶段上限分开运行，不能同时启用。

## 运行

更新并重启修复版 Future 服务端，然后：

```bash
# 同一 Spatial 10 个任务，每任务 3 个初态；E=10，实际 fine cap=5、coarse cap=6。
bash scripts/run_time.sh eval 0 --port 19930 \
  --suites libero_spatial --tasks 10 --trials 3 \
  --stage-aware \
  --output "$PWD/results/spatial_stage_cap56"

# 另一个方案：精细阶段允许最多提前 2 步，粗操作仍最多 4 步。
bash scripts/run_time.sh eval 0 --port 19930 \
  --suites libero_spatial --tasks 10 --trials 3 \
  --stage-aware --stage-fine-max-k 2 --stage-coarse-max-k 4 \
  --output "$PWD/results/spatial_stage_cap24"
```

可以通过 `--stage-config` 指定其他冻结的运动配置。若显式指定 `--candidates`，必须包含阶段上限以下的候选；精细上限 0 需要包含 0。候选初始值默认选择不超过 4 的最大候选，上限 0 会在第一次决策立即生效。

评估脚本读取 LIBERO 观测中的 `robot0_eef_pos` 和 `env.sim.data.time`，将已执行夹爪命令传给状态机。真实机器人适配时应传入控制时间戳与已测末端位置，不能把耗时统计代替物理运动时间。

## 日志与验证边界

- `run.json`：完整解析后的 StageConfig 和 CLI 参数，包括请求上限、硬上限和实际生效上限；启动时也打印 `STAGE_K_CAPS`。
- `actions.jsonl`：控制时间、末端位置、实际夹爪命令、env.step 墙钟耗时。
- `decisions.jsonl`：stage、特征、触发原因、请求/生效上限、计时需求、实际 k、预算不可行及上限限制标志。
- `handovers.jsonl`：该交接所属阶段、k 与上限、实际覆盖和等待。
- `summary.json`：阶段占比计数、每阶段 k 分布、受上限限制次数和每阶段等待总量。

新增状态机与真实后台线程回归测试验证 coarse/fine 条件、滞回、k=0、上限强制下降和块级交接。阶段功能未完成新的 DGX 闭环成功率评测；应与修复版固定 k=4 及仅计时 cap=4 在相同任务、初态和种子下比较。
